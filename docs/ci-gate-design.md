# CI 安全回归门禁：设计与风险分析

状态：设计，随实现一同审查。日期 2026-11-15，基于 `main` 的 `43b5640`。

## 1. 目标与边界

在 CI/CD 中比较两次扫描（基线与当前），按使用者明确给出的条件决定流水线是否继续：

- 新增的确认漏洞；
- 确定性覆盖率下降；
- 不可比较的安全结果。

不做的事：

- 不改变 `granttrace diff` 的默认行为。不加门禁参数时，终端输出、JSON 输出和退出码（`0` 完成、`2` 输入无效）与 `43b5640` 完全一致。
- 不改变扫描器、判定规则、`compare_reports` 的分类和 `comparison_schema_version`。
- 不访问网络，不需要比较密钥，不读取凭据。
- 门禁通过**不表示 API 安全**，只表示启用的条件没有出现，并且这一点被核实（或在使用者明确允许时依赖其声明的假设）。

## 2. 命令行

门禁是 `granttrace diff` 的可选参数，不新增子命令：

| 参数 | 含义 |
|---|---|
| `--fail-on-new` | 新增确认漏洞时阻断；不能证明当前的确认漏洞已在基线中存在时同样阻断 |
| `--fail-on-coverage-decrease` | 确定性覆盖率下降时阻断 |
| `--fail-on-not-comparable` | 任何一个确认漏洞不可比较时阻断 |
| `--gate-allow-assumptions` | 允许依赖 `--assume-*` 声明的结论参与通过判断；必须与至少一个 `--fail-on-*` 一起使用 |
| `--github-actions` | 以 GitHub Actions 工作流命令输出注解，并把 Markdown 摘要追加到 `$GITHUB_STEP_SUMMARY` |

命名沿用扫描命令的 `--fail-on-vuln` / `--fail-on-error` 风格。参数不能缩写（`allow_abbrev=False` 已生效）。

## 3. 退出码

| 退出码 | 含义 | 何时出现 |
|---|---|---|
| `0` | 比较完成；启用门禁时表示每个启用条件都已核实成立 | 不加 `--fail-on-*` 时总是 `0`（与现在相同） |
| `1` | **发现回归**：启用的条件被违反，且这一点有可比较的证据 | 新增确认漏洞；覆盖率下降 |
| `2` | 输入或参数无效，或输出无法写入；没有门禁结论 | 与现在相同，另加门禁参数的错误组合 |
| `3` | **无法核实**：启用的条件既没有被证明违反，也没有被证明成立 | 不可比较、证据不足、未获准的假设、当前报告没有任何确定结论 |

优先级 `2 > 1 > 3 > 0`。同时存在已核实的回归和无法核实的部分时返回 `1`，避免把已证实的回归降级为「无法核实」。

所有非零退出码在 GitHub Actions 中都会让步骤失败，所以默认是 **fail-closed**。若团队只想在 `1` 时阻断、把 `3` 当作提醒，需要在工作流中显式写出（例如 `continue-on-error` 加判断），这本身就是一项明确配置。

`3` 是新增的退出码。仓库内已有脚本 `scripts/verify_pr42_adversarial.py` 使用 `3`，但那是验证脚本，不是 `granttrace` 命令；`granttrace` 本身此前只使用 `0`、`1`、`2`。

## 4. 判断规则

门禁只读取比较结果和两份报告中每项检查的判定状态，不重新分类。设：

- **有效状态**：`diff` 给出的状态；但未使用 `--gate-allow-assumptions` 时，依赖假设的 `new` / `persisting` / `resolved` 一律视为 `not_comparable`。
- **基线已核实安全**：基线中这项检查（检查、操作、主体）的判定全是 SECURE / PUBLIC / AUTHORIZED，且有实际请求支撑。
- **确定结论**：判定是上述三者或 CONFIRMED，且有实际请求支撑（与 `diff`、扫描器的覆盖率规则相同）。

### 4.1 前提条件（对每个启用条件都适用）

任一不满足，该条件的结果至多为「无法核实」（`3`），不会是「通过」：

| 代码 | 条件 |
|---|---|
| `comparison_blocked` | `comparability.blocking` 非空（目标、身份、配置无法核对或已变化，或有无法解析且可能是确认漏洞的记录） |
| `assumptions_not_allowed` | 比较使用了 `--assume-*`，但没有 `--gate-allow-assumptions` |
| `no_conclusive_results` | 当前报告没有任何确定结论（例如目标不可达，全部 ERROR）；否则两份空报告会「通过」 |

### 4.2 `--fail-on-new`

| 结果 | 情况 | 代码 |
|---|---|---|
| 违反（`1`） | 有效状态为 `new` 的确认漏洞 | `new_finding` |
| 无法核实（`3`） | 当前的确认漏洞有效状态不是 `new` 或 `persisting`（首次发现、新操作、范围变化、基线未核实、没有请求支撑、主体不明……） | `confirmed_not_comparable` |
| 无法核实（`3`） | 基线已核实安全的检查，当前没有确定结论或已不存在（包括操作被移除） | `no_longer_verified` |
| 无法核实（`3`） | 基线已核实安全的检查，当前新出现 PUBLIC 或 AUTHORIZED，而该操作的规范、策略或资源有变化 | `accepted_after_declaration_change` |

后两行是本设计的关键：只看「当前没有 CONFIRMED」会把下面两种情况误判为没有回归：

1. 当前扫描对某项检查没有得到结论（ERROR、SKIPPED、INCONCLUSIVE，或判定没有请求支撑），漏洞可能存在却没被测到。
2. 被测改动同时修改了判定依据，例如在规范中去掉某个操作的 `security`，或在策略中声明 visitor 可以访问，于是新的越权被判为 PUBLIC / AUTHORIZED。

`persisting` 的确认漏洞**不会**让 `--fail-on-new` 失败：门禁回答的是「有没有变差」。要求当前没有任何确认漏洞，应在扫描时使用 `--fail-on-vuln`。

### 4.3 `--fail-on-coverage-decrease`

| 结果 | 情况 | 代码 |
|---|---|---|
| 违反（`1`） | 基线有确定结论、当前没有的检查（含被移除的操作） | `conclusive_check_lost` |
| 违反（`1`） | 报告统计中的确定性覆盖率百分比下降（例如新增了无法得到结论的操作） | `coverage_pct_decreased` |

与 `diff` 输出的 `coverage.decreased` 定义完全一致。

### 4.4 `--fail-on-not-comparable`

| 结果 | 情况 | 代码 |
|---|---|---|
| 无法核实（`3`） | 任一确认漏洞（基线或当前）的有效状态为 `not_comparable` | `finding_not_comparable` |

这个条件本身就是「无法核实」，所以只产生 `3`。

### 4.5 总体结果

- 任一启用条件被违反 → `failed`，退出码 `1`；
- 否则任一条件无法核实 → `unverified`，退出码 `3`；
- 否则 `passed`，退出码 `0`。`verified` 仅在没有使用任何假设时为 `true`；允许假设时通过的结果标为「依赖使用者声明的假设，未经核实」，并列出这些假设。

## 5. 输出

- **终端**：默认摘要保持原样，其后追加门禁段落：总体结果和退出码、每个条件的结果、决定结果的条目（最多 50 条，其余见 JSON），以及「通过不代表 API 安全」的说明。
- **JSON**（`--export-json`）：仅在使用 `--fail-on-*` 时增加顶层 `gate` 对象（`gate_schema_version` 1），只含枚举值、Finding ID、检查名、操作模板、主体和判定，与 `diff` 的隐私约束相同。不加门禁参数时 JSON 与现在逐字节相同。
- **GitHub Actions**（`--github-actions`）：
  - 输出报告内容（摘要、门禁条目）之前打印 `::stop-commands::<随机令牌>`，之后用该令牌恢复，令报告中的任何文字都不会被执行为工作流命令；
  - 恢复后输出注解：违反项为 `error`，无法核实项为 `warning`，总体结果一条（失败或无法核实为 `error`，依赖假设通过为 `warning`，核实通过为 `notice`）。每级最多 10 条（GitHub 对单个步骤的显示上限），注解内容按工作流命令规则转义 `%`、`\r`、`\n`；
  - `$GITHUB_STEP_SUMMARY` 存在时追加 Markdown 摘要；来自报告的文字（操作、主体）除字母、数字、空格、`/`、`{`、`}`、`-` 外一律写成 HTML 数字实体，无法形成链接、图片、HTML 或表格结构；最多 100 行条目。变量不存在时只在 stderr 提示，不算错误；写入失败返回 `2`。
  - 不加 `--fail-on-*` 也可以使用：只输出摘要文件和受保护的日志，不输出注解。

## 6. 风险分析

| # | 风险 | 后果 | 措施 | 残余 |
|---|---|---|---|---|
| R1 | 不可比较、证据不足或假设被当作通过（fail-open） | 回归进入主干 | 4.1 的三个前提；`--fail-on-new` 的三类「无法核实」；假设默认不计入；随机化测试用独立参考实现核对「通过 ⇒ 条件成立」 | 报告未签名（R6） |
| R2 | 默认行为被改变 | 已有自动化受影响 | 全部为新参数；测试比对不加参数时的终端输出和 JSON 与 `43b5640` 一致 | 无 |
| R3 | 退出码含义含糊或冲突 | CI 误放行 | `1`/`3` 区分已证实与无法核实，`2` 不变，优先级固定且文档化；任何非零默认都阻断 | 使用者主动放行 `3` 是其明确选择 |
| R4 | 新增或删除端点、规范变化 | 误报或漏报 | 新端点上的确认漏洞、删除端点、变化端点上的漏洞一律 `3`，交给人工审查 | 正常的接口变更也会触发 `3`，属预期 |
| R5 | 被测改动修改判定依据（规范 `security`、策略），把越权变成 PUBLIC / AUTHORIZED | 回归被「声明」掩盖 | `accepted_after_declaration_change`；文档要求配置取自受保护的基线分支 | 两次扫描都使用被篡改的配置时无法发现，需要配置来自可信来源 |
| R6 | 基线不可信（报告未签名，伪造的基线把漏洞变成 `persisting`） | `--fail-on-new` 放行 | 文档要求基线由受信任的工作流产生，不从 PR 文件读取；建议同时使用 `--fail-on-vuln` | 报告完整性无法验证，`comparability.not_verified` 始终列出 |
| R7 | PR 代码与门禁运行在同一个 runner 上，可修改报告文件 | 门禁被绕过 | 文档要求被测服务运行在容器中、不挂载工作区，密钥只给扫描步骤，外部贡献者的 PR 需审批后运行 | 无法在工具内消除 |
| R8 | 报告文字注入 GitHub 工作流命令（行首 `::`；旧格式 `##[` 在行内任意位置有效，包括仍被处理的 `set-output`）或 Markdown | 伪造注解、篡改步骤输出、钓鱼链接 | 终端输出在任何模式下转义 `##[` 和行首 `::`（`safe_log_line`）；`--github-actions` 另用 `stop-commands` 包裹全部报告文字；注解与摘要转义 | 已修复（合并前审查发现默认输出不受保护）。兼容性例外：含这两种标记的文字在终端中以 `\uXXXX` 形式显示，JSON 不变 |
| R9 | 比较密钥泄露（fork PR 无法读取 secrets；`pull_request_target` 运行 PR 代码会泄露） | 指纹可被伪造 | 示例使用 `pull_request`、`permissions: contents: read`、`persist-credentials: false`，密钥只在扫描步骤；缺少密钥时门禁返回 `3` 而不是放行 | 使用者自行修改工作流 |
| R10 | 输出过大 | 摘要被截断、注解不显示 | 注解每级 10 条，摘要 100 行，终端门禁条目 50 行，完整内容在 JSON | 无 |
| R11 | Windows 与 Python 3.9 | 便携版不可用 | 不新增依赖；只用 3.9 可用的语法；输出全部为 ASCII；便携版验证脚本增加门禁步骤 | 无 |
| R12 | 参数误用 | 以为启用了门禁 | `--gate-allow-assumptions` 单独使用返回 `2`；门禁段落在终端写明启用了哪些条件 | 无 |

## 7. 验证计划

- 单元测试：每个条件 × 每种结果；三个前提；优先级；假设默认不计入、允许后标注未核实；`accepted_after_declaration_change`；`no_longer_verified`（含删除操作、没有请求支撑）。
- 安全反例：不可比较、证据不足、人工假设、空报告、伪造的 Markdown / 工作流命令，均不得得到 `0`。
- 随机化测试：随机生成报告对，用独立实现的参考规则核对门禁结论；断言「通过」时不存在任何违反或无法核实的条目。
- 默认行为：不加门禁参数时终端输出和 JSON 与 `43b5640` 相同。
- 端到端：真实扫描本机测试服务（回归、修复、首次发现、不可比较），以及 GitHub Actions 中实际运行一次核实通过的门禁。
- Windows 便携版：打包后的 `granttrace diff` 返回 `0`、`1`、`3`，并写出步骤摘要。
- Python 3.9 / 3.10 / 3.11 / 3.12 / 3.13 / 3.14 本地矩阵，Ruff、Mypy、CodeQL。
